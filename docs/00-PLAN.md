# TrainCov — план реалізації MVP

## 1. Що це

PWA-застосунок, який для обраного залізничного маршруту в Польщі показує, **де і коли зникне мобільний інтернет**. Користувач обирає рейс (потяг) і оператора, застосунок будує «стрічку маршруту» з мертвими зонами, а в дорозі за GPS та швидкістю потяга показує зворотний відлік: *«Інтернет зникне через 4:20, діра триватиме ~7 хв»*.

## 2. Межі MVP

### Входить у MVP
1. Вибір рейсу з реальних даних (GTFS `polish_trains.zip` від mkuran.pl) — маршрут, станції, планові часи.
2. Шар мертвих зон із **детермінованих джерел**: тунелі/виїмки з OSM + ручний файл сегментів (заповнюється власними спостереженнями).
3. Живе відстеження: GPS → проєкція на колію → поточний км → згладжена швидкість.
4. Прогноз: час до наступної мертвої зони, її тривалість, часові мітки для всіх зон і станцій попереду.
5. Офлайн-робота: маршрутний пакет, карта (PMTiles), UI повністю працюють без мережі.
6. Логер якості зв'язку (probe RTT) з експортом JSON — фундамент майбутнього краудсорсингу.

### НЕ входить у MVP (покращення після)
- Бекенд для збору замірів (Cloudflare Worker + D1), мерж чужих даних.
- Модель покриття з OpenCelliD / BeaconDB (вишки + радіуси).
- Рельєф (Copernicus DEM), line-of-sight.
- Real-time запізнення та утруднення з PLK API (`pdp-api.plk-sa.pl`).
- Диференціація по типу рухомого складу (Pendolino vs PolRegio).
- Нативний Android-збір сигналу в dBm.
- Оператор у MVP — це лише **тег** у налаштуваннях і в логах замірів; окремих карт покриття на оператора ще немає (зони спільні). Це чесне обмеження, яке зникне, коли з'явиться шар даних по операторах.

## 3. Ключові обмеження середовища (визначають архітектуру)

| Обмеження | Наслідок |
|---|---|
| Браузер не дає рівень сигналу (dBm); `navigator.connection` — тільки Chrome/Android | Якість зв'язку міряємо **активним зондуванням** (fetch з таймаутом → RTT / фейл) |
| iOS вбиває JS при погашеному екрані | Wake Lock API + явна вимога «тримай екран увімкненим у режимі поїздки» |
| У поїздці зв'язку немає за визначенням | **Offline-first**: усе потрібне (маршрут, зони, тайли) завантажується ДО поїздки |
| Ліміти PLK API (100 req/год Basic) | У MVP PLK API не використовуємо взагалі; GTFS-файл обробляється **офлайн-пайплайном**, не клієнтом |
| GTFS `polish_trains.zip` ~десятки МБ | Клієнт ніколи не бачить GTFS: Node-пайплайн ріже його на маленькі route-бандли (JSON) |

## 4. Архітектура

```
┌────────────────────────── build-time (Node, локально/CI) ──────────────────────────┐
│  GTFS polish_trains.zip ─┐                                                         │
│  Overpass API (тунелі)  ─┼─> scripts/pipeline/ ─> public/data/                     │
│  manual-zones.json      ─┘        │                 ├─ index.json  (список рейсів) │
│                                   │                 └─ routes/{tripId}.json        │
└───────────────────────────────────┼────────────────────────────────────────────────┘
                                    ▼
┌────────────────────────────── runtime (PWA, браузер) ──────────────────────────────┐
│  React UI                                                                          │
│   ├─ RoutePicker      — вибір рейсу + оператора, завантаження бандла в IndexedDB   │
│   ├─ TripScreen       — стрічка маршруту, карта, countdown                         │
│   └─ Logger           — probe RTT + GPS → IndexedDB → експорт JSON                 │
│  Core (чисті модулі без React)                                                     │
│   ├─ linref.ts        — проєкція GPS на полілінію, км маршруту (turf)              │
│   ├─ speed.ts         — згладжування швидкості                                     │
│   ├─ eta.ts           — прогноз часу до зон (GPS-швидкість + профіль з розкладу)   │
│   └─ probe.ts         — активне зондування мережі                                  │
│  Storage: Dexie (IndexedDB) · Map: MapLibre GL + PMTiles · SW: vite-plugin-pwa     │
└────────────────────────────────────────────────────────────────────────────────────┘
```

**Принцип:** ніякого власного бекенду в MVP. Статичні дані генеруються пайплайном і хостяться як файли (Cloudflare Pages / Vercel). Єдиний мережевий виклик у дорозі — probe (легкий GET на публічний 204-ендпоінт).

## 5. Технології

- **Vite + React 18 + TypeScript**, `vite-plugin-pwa` (Workbox).
- **MapLibre GL JS** + **PMTiles** (Protomaps) — офлайн-карта одним файлом.
- **@turf/turf** — `nearestPointOnLine`, `length`, `along`, лінійна референція.
- **Dexie.js** — IndexedDB (маршрутні бандли, заміри, налаштування).
- **Node 20+ пайплайн**: `gtfs-utils` або власний парсер CSV (`csv-parse`), `unzipper`, Overpass QL через `fetch`.
- Хостинг: **Cloudflare Pages** (статика + дані). Доменна логіка вже знайома по власному домену.

## 6. Ключові структури даних

### Route bundle (`routes/{tripId}.json`)
```jsonc
{
  "tripId": "IC_1234_2026-08-02",
  "name": "IC 1234 Wrocław Gł. → Warszawa Centralna",
  "carrier": "IC",
  "shape": { "type": "LineString", "coordinates": [[lng, lat], ...] }, // спрощена (douglas-peucker ~10м)
  "lengthKm": 354.2,
  "stops": [
    { "id": "wroclaw-gl", "name": "Wrocław Główny", "km": 0, "arr": null, "dep": "14:35" },
    { "id": "...", "name": "...", "km": 58.1, "arr": "15:07", "dep": "15:09" }
  ],
  "speedProfile": [                    // виведено з розкладу: середня швидкість між зупинками
    { "fromKm": 0, "toKm": 58.1, "kmh": 109 }
  ],
  "deadZones": [
    { "id": "dz-01", "fromKm": 45.2, "toKm": 48.7, "kind": "tunnel|cutting|manual",
      "severity": "none|weak", "source": "osm|manual", "note": "..." }
  ]
}
```

### Замір (IndexedDB `measurements`)
```jsonc
{ "ts": 1722600000000, "lat": 51.1, "lng": 17.03, "acc": 12,
  "routeKm": 45.7, "tripId": "...", "operator": "play",
  "probeRttMs": 240, "probeOk": true, "effectiveType": "4g|null" }
```

## 7. UX (мінімум)

Три екрани:
1. **Home / RoutePicker** — пошук рейсу (станція від/до або номер потяга), вибір оператора, кнопка «Завантажити для офлайн».
2. **Trip** — головний екран: вертикальна стрічка маршруту (станції + зони з часовими мітками), зверху великий блок стану: `🔴 через 4:20 — мертва зона, ~7 хв` / `🟢 наступна діра через 38 хв`. Перемикач на карту.
3. **Log** — статус логера, кількість замірів, кнопка експорту JSON.

Дизайн — мобільний-only, тёмна тема, великі цифри (телефон лежить на столику у потязі).

## 8. Розбиття на задачі

Кожна задача = самодостатній інкремент; після кожної застосунок запускається і робить щось нове.

| # | Файл | Що додається | Що працює після |
|---|---|---|---|
| 1 | `01-skeleton-map.md` | Скелет Vite+React+TS, MapLibre, хардкод-маршрут | Карта з лінією Wrocław→Warszawa у браузері й на телефоні |
| 2 | `02-data-pipeline.md` | Node-пайплайн: GTFS → route bundles | `npm run pipeline` генерує реальні бандли; апка рендерить один із них |
| 3 | `03-route-picker.md` | UI вибору рейсу + оператора, index.json | Можна знайти реальний рейс і відкрити його маршрут |
| 4 | `04-gps-tracking.md` | GPS → км маршруту, швидкість, стрічка | Точка «я» рухається по стрічці/карті, видно км і км/год |
| 5 | `05-dead-zones.md` | Тунелі з Overpass + manual-zones → шар зон | Зони видно на стрічці й карті |
| 6 | `06-eta-engine.md` | Прогноз: countdown, часові мітки | Головна фіча: «інтернет зникне через X хв» |
| 7 | `07-offline-pwa.md` | SW, PMTiles, кеш бандлів, Wake Lock | Все працює в airplane mode |
| 8 | `08-probe-logger.md` | Probe RTT логер + експорт | Заміри пишуться і експортуються — сировина для v2 |

Залежності лінійні: 1→2→3→4→5→6→7→8. Задачі 5 і 8 можна за бажання поміняти місцями з 7.

## 9. Definition of Done для MVP

- [ ] На телефоні (Chrome/Android і Safari/iOS) можна: обрати рейс → завантажити пакет → вимкнути мережу → сісти в потяг → бачити позицію, швидкість і countdown до зон.
- [ ] Зони показуються щонайменше з двох джерел: OSM-тунелі + ручний файл.
- [ ] Прогноз деградує граційно: немає GPS-швидкості → профіль із розкладу; немає GPS взагалі → таймлайн лише за розкладом.
- [ ] Логер накопичує заміри в IndexedDB і експортує валідний JSON.
- [ ] Lighthouse PWA: installable, працює офлайн.
