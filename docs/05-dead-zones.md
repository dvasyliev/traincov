# Задача 05 — Шар мертвих зон (OSM-тунелі + ручні сегменти)

## Мета
Наповнити `deadZones` реальними даними з двох детермінованих джерел: тунелі/виїмки з OSM (Overpass) і ручний файл власних спостережень. Зони рендеряться на стрічці та карті.

## Що працює після задачі
- Пайплайн кладе зони в кожен route bundle.
- На стрічці маршруту — червоні/жовті сегменти з довжиною; на карті — підсвічені ділянки колії.

## Кроки

### 5.1 Пайплайн: Overpass-виборка тунелів
Новий крок `scripts/pipeline/zones-osm.ts`:
- Для кожного бандла взяти bbox shape (+буфер 0.02°) і запит:
```
[out:json][timeout:120];
(
  way["railway"~"rail|light_rail"]["tunnel"="yes"](bbox);
  way["railway"~"rail|light_rail"]["cutting"="yes"](bbox);
);
out geom;
```
- Кешувати відповідь у `.cache/overpass/{hash(bbox)}.json` (Overpass не любить повторні важкі запити; між запитами sleep 2 c; мати fallback-дзеркало `overpass.kumi.systems`).

### 5.2 Матчинг way → сегмент маршруту
Проблема: тунельний way — це *якась* колія у bbox, не обов'язково наша. Алгоритм:
1. Для кожного way взяти його вершини; порахувати відстань кожної до shape (`nearestPointOnLine`).
2. Way вважається «нашим», якщо ≥ 80% вершин ближче 50 м до shape.
3. Для матчнутого way: `fromKm = min(location)`, `toKm = max(location)` по спроєктованих вершинах.
4. Мержити сегменти, що перетинаються або ближчі 0.2 км один до одного (тунель часто нарізаний на кілька ways).
5. Викинути сегменти коротші 0.15 км для `cutting` (дрібні виїмки не варті уваги; тунелі лишати будь-які).
- Мапінг: `tunnel` → `severity: 'none'` (немає інтернету), `cutting` → `severity: 'weak'`.

### 5.3 Ручний файл
`scripts/pipeline/manual-zones.json`:
```jsonc
[
  { "match": { "tripNameContains": "Wrocław" },   // або "lineRef": "271"
    "zones": [
      { "fromKm": 132.0, "toKm": 139.5, "severity": "none",
        "note": "ліс за Ostrów Wlkp., перевірено 2026-07-xx, Play" }
    ] }
]
```
- Km тут — км **маршруту конкретного бандла**, тому `match` по назві рейсу. (Стабільний км лінії PLK — покращення поза MVP; зафіксувати це в note файлу.)
- Пайплайн мержить manual поверх OSM (manual пріоритетніший при перетині).
- Стартово заповнити 2–3 зонами з власного досвіду поїздок Wrocław→Warszawa — щоб продукт одразу мав «м'ясо».

### 5.4 Валідація в пайплайні
- `0 ≤ fromKm < toKm ≤ lengthKm`, інакше — error і skip.
- Сортувати за fromKm; після мержу зони не перетинаються.
- У index.json додати `zonesCount` для кожного рейсу.

### 5.5 UI: зони на стрічці
- Сегмент стрічки заливається: `severity none` → червоний `#ef4444` зі штрихуванням; `weak` → янтарний `#f59e0b`.
- Лейбл: `⛔ 3.5 км · тунель` / `⚠️ 7.5 км · слабкий сигнал`.
- Тап по зоні → bottom-sheet: джерело (osm/manual), note, довжина.

### 5.6 UI: зони на карті
- В бандл додати (пайплайном) готові LineString-фрагменти зон (`turf.lineSliceAlong(shape, fromKm, toKm)`) — щоб клієнт не різав геометрію сам. Рендер: окремий line-layer поверх маршруту, ширший, з кольором за severity.

## Обмеження
- Зони спільні для всіх операторів (тунель — обʼєктивний; manual-зони позначені оператором у note, але UI поки не фільтрує).
- Немає радіо-моделі (вишки/рельєф) — свідомо: детерміновані джерела дають高 точність без складності.

## Пастки
- Overpass `out geom` повертає координати прямо у way — не потрібен окремий запит nodes.
- Паралельні колії (двоколійна лінія = 2 ways у тунелі) — мерж у кроці 5.2.4 це закриває.
- Здвоєні станційні тунелі в містах (Warszawa Śródmieście!) — перевірити очима результат для W-wa: тунель середмістя має знайтися. Це хороший smoke-test.

## Acceptance criteria
- [ ] Для маршруту через Warszawa Centralna пайплайн знаходить варшавський тунель (~2 км) автоматично.
- [ ] Manual-зона з файлу з'являється на стрічці з приміткою.
- [ ] Зони на карті лежать точно на колії.
- [ ] Пайплайн з кешем Overpass відпрацьовує повторно без мережевих запитів.
